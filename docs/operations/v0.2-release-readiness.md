# v0.2.0 正式版发布就绪清单

- 状态：rc.33 已发布；rc.34 统一账号授权界面
- 稳定性观察基线：`v0.2.0-rc.17`
- 当前候选版本：`v0.2.0-rc.34`
- 快照日期：2026-08-28

本文把 v0.2.0 正式版的事实证据、发布门禁和维护者操作拆开。快照日期之后的
Issue、CI、镜像和现场运行结果必须在正式评审时重新确认，本文不能替代实时检查。

## 1. 当前结论

维护者于 2026-08-25 确认 rc.17 稳定性观察通过，不再把原计划日期作为硬阻断。
rc.18 加入实验性夸克 Provider 和 `0008_provider_operations` 迁移。其公开双架构
镜像已生成，但从 rc.17 的现场一键更新发生安全回滚，且旧终态没有保存失败阶段。
rc.19 修复该诊断缺口，并确认失败发生在创建数据快照阶段。现场权限证据显示 NAS
把 `/data` 和 SQLite 文件映射为 mode `000`；rc.20 以唯一 `DAC_OVERRIDE` 能力修复
受限 updater 的访问，但 Docker Inspect 对 capability 和 security option 的规范化
触发了身份误判与 helper 重启。rc.21 接受这些严格等价形式，但现场 Engine 又
静默丢弃非 canonical capability。rc.22 改用 `CAP_DAC_OVERRIDE` 并在启动前回读
验证，同时保留其他隔离边界。rc.23 进一步修复夸克自动创建目标子目录、失败状态
回写和脱敏诊断；其现场重试暴露目录创建请求返回业务码 `23006`。rc.24 改用完整
路径建目录契约，公开镜像升级和夸克单项转存已由维护者现场确认成功。后续
`32003` 已确认是目标账号空间不足；腾出空间后单项重试成功。rc.25 增加按筛选范围
批量重试失败文件，其公开升级和批量操作已由维护者现场确认通过。rc.26 新增实验性
123 云盘 Provider；真实账号的只读、跨账号单项转存和根目录建目录三个探针均已
通过，CI、双架构镜像和一键升级也已完成。真实订阅随后暴露任务引擎通用根目录
`root` 与上游数字根目录 `0` 不一致，首次目标目录查询失败。rc.27 规范化这一边界、
补充 123 脱敏错误详情，并已完成公开镜像、一键升级。真实订阅随后进入写入阶段，
但对子目录叶子文件逐项调用分享转存接口时返回业务码 `101304`。成功探针只验证过
分享根层单项；rc.28 改用 `Etag + Size` 同盘内容复用逐文件保存，并继续通过目标
目录对账确认最终结果，公开升级和真实订阅复测均已通过。rc.29 新增实验性百度
Provider，使用 BDUSS 读取分享和执行转存，使用 OpenList OpenAPI 刷新令牌浏览
账号盘、查重和自动建目录；四项独立真实探针已通过。rc.29 的 CI、GitHub
Prerelease 以及 GHCR、Docker Hub 双架构镜像均已完成，两个 Registry 的 OCI
索引摘要同为 `sha256:55a7a795891287ed84b116ca60f2252d1fcf34e46a2249acfabc0981344cdde2`。
rc.30 在此基础上新增 123 与百度本地扫码登录、分步授权页面、百度 OpenList 引导，
并修复贴吧 `user_id` 与网盘 `uk` 跨命名空间比较造成的同账号误判。rc.30 的 PR
#163、主分支 CI、GitHub Prerelease 及两个 Registry 双架构镜像均已通过；OCI 索引
摘要同为 `sha256:309b17b3a49cee6c7c538e39e8a4e53a059762baa4a7ad7645bdecde617db5bf`。
rc.31 补齐夸克本地扫码登录，并明确 Cookie 已覆盖完整转存链路；OpenList OpenAPI
只保留为需要配套 AppID/SignKey 的可选账号盘通道；维护者已确认真实登录成功。
rc.32 进一步按 Provider 的续期协议展示授权方式，但现场验收发现 123 公共 OpenList
OAuth 因节点缺少企业应用配置跳转 404，百度 AListGo 入口也指向不存在的页面。rc.33
因此移除 123 公共托管方式，仅保留自有应用，并把百度改为官方文档使用的直接 OAuth
授权地址。rc.34 不改变 Provider 协议和数据结构，统一四个网盘的 OpenAPI 绑定流程、
私有登录与开放平台能力说明，并在账号管理全流程中补齐本地品牌 Logo。

维护者已经确认 rc.17 当前运行正常，也确认 NAS updater 演练已经完成。因此
[Issue #128](https://github.com/josephyin/MediaSync/issues/128) 后续只做证据核对和
关闭结论，不重复执行现场演练。若 Issue 中现有记录和实际演练结论不一致，应补充
实际平台、镜像版本、结果和日期，不得把“记录未同步”误写成“演练未完成”。

实验性夸克能力已由维护者批准进入 rc.18。它不改变 rc.17 精确标签或回滚镜像；
正式版 Go/No-Go 仍需在 [Issue #34](https://github.com/josephyin/MediaSync/issues/34)
记录 rc.34 的最终验收证据。

## 3. rc.34 发布验收

1. 合并账号授权界面统一 PR 后，从 `main` 创建并推送唯一的 `v0.2.0-rc.34` 精确标签。
2. 确认发布工作流同时生成 GHCR 与 Docker Hub 的 `linux/amd64`、`linux/arm64`。
3. 从 rc.33 使用完整 `/data` 备份执行一次升级，确认登录、已有阿里/夸克/123/百度账号、
   订阅和任务历史正常。
4. 确认四个网盘的账号卡片、添加向导和 OpenAPI 弹窗均显示对应 Logo；授权页面明确
   区分私有登录与 OpenAPI 的必需、可选关系，并只展示各 Provider 实际支持的方式。
5. 核对 API、Scheduler、Worker、Updater 与 Appliance 日志不包含 Refresh Token、
   Access Token、BDUSS 或携带这些字段的完整请求 URL。
6. 发现异常时记录平台、架构、日志、数据影响和恢复步骤；必要时回滚 rc.17。

## 4. 正式版评审

维护者按以下顺序执行，并把命令版本、提交 SHA 和结果链接写入 Issue #34：

1. 确认 rc.17 观察期及 rc.25 至 rc.34 验收没有未处置的 P0/P1、重复转存、任务丢失或
   不可恢复的数据问题。
2. 检查开放 Issue 和 PR，明确每一项是否阻断 v0.2.0。
3. 从干净检出的待发布提交运行仓库 CI 对应的后端、前端、迁移及静态检查。
4. 使用正式候选的精确镜像执行启动、登录、账号验证、订阅扫描、任务执行和健康
   检查冒烟验证；核对已有备份恢复演练证据，不重复执行演练。
5. 确认 rc.17 回滚镜像和发布前 `/data` 备份可用。
6. 在 Issue #34 写明 Go/No-Go 决定；只有 Go 才进入版本号和标签操作。

不要提前创建 `v0.2.0` 标签，也不要用移动的 `rc` 或 `latest` 标签代替精确版本
做验收。

## 5. Go 之后的发布步骤

1. 把应用版本、README、部署示例、Docker Hub Overview 和 CHANGELOG 从 rc.34
   更新为 `v0.2.0`，并注明正式版没有额外数据库或 Provider 行为变化。
2. 审核最终 diff，确认只包含批准的发布收口变更。
3. 在 `main` 上完成最终 CI 后创建并推送 `v0.2.0` 精确标签。
4. 按[容器镜像发布手册](container-release.md)确认发布工作流成功。
5. 在未登录环境验证 GHCR 与 Docker Hub 均包含 `linux/amd64` 和 `linux/arm64`，
   并核对两个 Registry 的产物来自同一提交。
6. 确认 GitHub Release 为正式版本而非 prerelease，`latest` 指向 v0.2.0。
7. 使用公开精确镜像完成一次干净安装和一次从 rc.17 升级的发布后冒烟检查。
8. 发布结果和已知限制写入 Issue #34 后关闭里程碑。

任一步失败都只修复失败环节；不得覆盖已经发布的精确标签。镜像构建成功、说明
同步成功和线上冒烟成功是三个独立结论，必须分别验证。
