本文把 v0.2.0 正式版的事实证据、发布门禁和维护者操作拆开。快照日期之后的
Issue、CI、镜像和现场运行结果必须在正式评审时重新确认，本文不能替代实时检查。

## 1. 当前结论

截至本次审计，没有发现需要立即修改 rc.17 的已知代码级阻断项。rc.17 继续作为
稳定性观察基线，正式版当前唯一硬门槛是完成八周观察并由维护者在
[Issue #34](https://github.com/josephyin/MediaSync/issues/34) 作出 Go/No-Go 结论。

维护者已经确认 rc.17 当前运行正常，也确认 NAS updater 演练已经完成。因此
[Issue #128](https://github.com/josephyin/MediaSync/issues/128) 后续只做证据核对和
关闭结论，不重复执行现场演练。若 Issue 中现有记录和实际演练结论不一致，应补充
实际平台、镜像版本、结果和日期，不得把“记录未同步”误写成“演练未完成”。

正式评审前冻结 rc.17 运行行为。除 P0/P1 缺陷、安全问题或数据完整性问题外，
Provider 新功能、界面改造和架构重构都不进入 v0.2.0。

## 5. Go 之后的发布步骤

1. 把应用版本、README、部署示例、Docker Hub Overview 和 CHANGELOG 从 rc.17
   更新为 `v0.2.0`，并注明正式版没有额外数据库或 Provider 行为变化。
2. 审核最终 diff，确认只包含批准的发布收口变更。
3. 在 `main` 上完成最终 CI 后创建并推送 `v0.2.0` 精确标签。
4. 按[容器镜像发布手册](container-release.md)确认发布工作流成功。
5. 在未登录环境验证 GHCR 与 Docker Hub 均包含 `linux/amd64` 和 `linux/arm64`，
   并核对两个 Registry 的产物来自同一提交。
6. 确认 GitHub Release 为正式版本而非 prerelease，`latest` 指向 v0.2.0。
7. 使用公开精确镜像完成一次干净安装和一次从 rc.17 升级的发布后冒烟检查。
8. 发布结果和已知限制写入 Issue #34 后关闭里程碑。

任一步失败都只修复失败环节；不得覆盖已经发布的精确标签。镜像构建成功、说明
同步成功和线上冒烟成功是三个独立结论，必须分别验证。
