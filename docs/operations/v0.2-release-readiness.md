# v0.2.0 正式版发布就绪清单

- 状态：稳定性观察已通过；rc.19 发布验收中
- 稳定性观察基线：`v0.2.0-rc.17`
- 当前候选版本：`v0.2.0-rc.19`
- 快照日期：2026-08-25

本文把 v0.2.0 正式版的事实证据、发布门禁和维护者操作拆开。快照日期之后的
Issue、CI、镜像和现场运行结果必须在正式评审时重新确认，本文不能替代实时检查。

## 1. 当前结论

维护者于 2026-08-25 确认 rc.17 稳定性观察通过，不再把原计划日期作为硬阻断。
rc.18 加入实验性夸克 Provider 和 `0008_provider_operations` 迁移。其公开双架构
镜像已生成，但从 rc.17 的现场一键更新发生安全回滚，且旧终态没有保存失败阶段。
rc.19 修复该诊断缺口；仍必须完成自己的 CI、双架构镜像和 rc.17 升级冒烟。

维护者已经确认 rc.17 当前运行正常，也确认 NAS updater 演练已经完成。因此
[Issue #128](https://github.com/josephyin/MediaSync/issues/128) 后续只做证据核对和
关闭结论，不重复执行现场演练。若 Issue 中现有记录和实际演练结论不一致，应补充
实际平台、镜像版本、结果和日期，不得把“记录未同步”误写成“演练未完成”。

实验性夸克能力已由维护者批准进入 rc.18。它不改变 rc.17 精确标签或回滚镜像；
正式版 Go/No-Go 仍需在 [Issue #34](https://github.com/josephyin/MediaSync/issues/34)
记录 rc.19 的最终验收证据。

## 3. rc.19 发布验收

1. 合并版本一致性 PR 后，从 `main` 创建并推送唯一的 `v0.2.0-rc.19` 精确标签。
2. 确认发布工作流同时生成 GHCR 与 Docker Hub 的 `linux/amd64`、`linux/arm64`。
3. 从 rc.17 使用完整 `/data` 备份执行一次升级，确认迁移、登录、原阿里云盘账号、
   订阅和任务历史正常。
4. 使用跨账号测试分享验证夸克账号、扫描和单项转存；不要用目标账号自己的分享。
5. 发现异常时记录平台、架构、日志、数据影响和恢复步骤；必要时回滚 rc.17。

## 4. 正式版评审

维护者按以下顺序执行，并把命令版本、提交 SHA 和结果链接写入 Issue #34：

1. 确认 rc.17 观察期和 rc.19 验收没有未处置的 P0/P1、重复转存、任务丢失或
   不可恢复的数据问题。
2. 检查开放 Issue 和 PR，明确每一项是否阻断 v0.2.0。
3. 从干净检出的待发布提交运行仓库 CI 对应的后端、前端、迁移及静态检查。
4. 使用正式候选的精确镜像执行启动、登录、账号验证、订阅扫描、任务执行和健康
   检查冒烟验证；核对已有备份恢复演练证据，不重复执行演练。
5. 确认 rc.17 回滚镜像和发布前 `/data` 备份可用。
6. 在 Issue #34 写明 Go/No-Go 决定；只有 Go 才进入版本号和标签操作。

不要提前创建 `v0.2.0` 标签，也不要用移动的 `rc` 或 `latest` 标签代替精确版本
做验收。

## 5. Go 之后的发布步骤

1. 把应用版本、README、部署示例、Docker Hub Overview 和 CHANGELOG 从 rc.19
   更新为 `v0.2.0`，并注明正式版没有额外数据库或 Provider 行为变化。
2. 审核最终 diff，确认只包含批准的发布收口变更。
3. 在 `main` 上完成最终 CI 后创建并推送 `v0.2.0` 精确标签。
4. 按[容器镜像发布手册](container-release.md)确认发布工作流成功。
5. 在未登录环境验证 GHCR 与 Docker Hub 均包含 `linux/amd64` 和 `linux/arm64`，
   并核对两个 Registry 的产物来自同一提交。
6. 确认 GitHub Release 为正式版本而非 prerelease，`latest` 指向 v0.2.0。
7. 使用公开精确镜像完成一次干净安装和一次从 rc.17 升级的发布后冒烟检查。
8. 发布结果和已知限制写入 Issue #34 后关闭里程碑。

任一步失败都只修复失败环节；不得覆盖已经发布的精确标签。镜像构建成功、说明
同步成功和线上冒烟成功是三个独立结论，必须分别验证。
