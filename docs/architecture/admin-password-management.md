# 管理员在线修改密码设计

- 状态：草案
- 日期：2026-07-30
- 目标里程碑：v0.2 Foundation
- 相关 Issue：[Issue #69](https://github.com/josephyin/MediaSync/issues/69)
- 相关决策：[ADR-0004：默认单容器 Appliance](adr/ADR-0004-single-container-appliance.md)

## 1. 背景

MediaSync 当前只有一个本地管理员账号。管理员密码来自 `ADMIN_PASSWORD`，默认
Appliance 会把它与运行时密钥一起持久化到：

```text
/data/config/runtime-secrets.json
```

用户可以在首次创建容器时指定密码，也可以修改环境变量并重建容器完成离线重置。
Web 管理后台目前没有修改密码入口，因此“首次登录后更换强密码”仍要求用户理解
容器环境变量和重建流程。

在线修改密码会同时改变认证、持久化配置和会话安全语义，属于 Credential 与安全
模型变化。按照项目治理规则，必须先确定设计契约，再提交运行时代码。

## 2. 目标

本设计为 v0.2 定义以下能力：

- 已登录管理员可以在 Web 管理后台修改自己的密码；
- 修改前必须再次验证当前密码；
- 新密码原子持久化到 `/data`，容器重启后继续有效；
- 密码修改成功后立即使所有旧会话失效；
- 离线 `ADMIN_PASSWORD` 重置仍然有效；
- 修改密码不重启 API、Scheduler、Worker 或整个容器；
- 密码、哈希、Cookie 和运行时密钥不得出现在日志、任务或 API 响应中。

## 3. 非目标

本阶段不实现：

- 多用户、角色、权限或管理员用户名修改；
- 找回密码、邮件验证码、二次验证或 Passkey；
- 登录失败限流和 IP 封禁；
- `SECRET_KEY` 或 `CREDENTIAL_ENCRYPTION_KEY` 在线轮换；
- 数据库保存管理员账号；
- Provider、Task Engine、Scheduler 或 Worker 行为变化；
- 远程修改高级 Compose 部署的 `.env` 文件。

登录限流属于独立安全能力，不得顺带扩大本实现 Issue。

## 4. 核心不变量

### 4.1 身份确认

- 只有持有有效管理员会话的请求可以修改密码。
- 请求必须同时提供当前密码、新密码和新密码确认值。
- 当前密码必须使用恒定时间比较验证。
- 新密码和确认值必须完全一致。
- 新密码不得与当前密码相同。
- 任一校验失败时，不得修改持久化文件、内存认证状态或会话版本。

### 4.2 密码规则

在线设置的新密码必须：

- 长度为 8 至 128 个 Unicode 字符；
- 不得为空白字符串；
- 不得等于当前密码；
- 不得等于内置初始值 `admin`。

v0.2 不强制大小写、数字和特殊字符组合。长密码短语是受支持的推荐形式。

镜像默认值 `admin` 只作为受信任局域网中的首次安装引导值保留。历史密码和离线
重置的兼容规则不在本设计 PR 中收紧；在线修改入口必须执行上述新规则。

### 4.3 单一写入口

运行时代码不得在 API 路由中直接写 JSON 文件或修改全局 Settings。密码读取、
校验、原子更新和会话修订号必须由唯一的管理员凭证组件负责。

建议接口：

```python
class AdminCredentialStore(Protocol):
    def verify(self, password: str) -> bool: ...

    def revision(self) -> int: ...

    def change_password(
        self,
        *,
        current_password: str,
        new_password: str,
    ) -> int: ...
```

`change_password()` 返回新的会话修订号。路由、会话验证和离线重置不得各自实现
另一套密码更新语义。

### 4.4 原子性

一次成功修改必须把“新密码”和“新会话修订号”视为同一个持久化单元：

```text
校验当前密码
    ↓
生成 revision + 1
    ↓
写同目录临时文件、flush、fsync
    ↓
原子替换 runtime-secrets.json
    ↓
fsync 配置目录
    ↓
更新 API 进程内凭证快照
    ↓
清除当前会话 Cookie
```

必须先完成持久化，再切换进程内状态。持久化失败时，旧密码和旧修订号继续有效，
接口返回失败；不得出现“当前进程接受新密码，但重启后恢复旧密码”的状态。

进程内快照切换必须是无 I/O、不可失败的操作。如果进程在原子替换后、内存切换前
崩溃，容器重启后以持久化的新密码和新修订号为准。

### 4.5 并发

密码更新必须在单进程锁内完成“重新验证当前密码 → 持久化 → 内存切换”。两个
使用相同旧密码同时到达的请求最多只能有一个成功。后到请求必须基于更新后的凭证
重新验证并失败，不能覆盖先到请求的新密码。

SQLite 不参与该锁，密码更新不得开启数据库事务。

### 4.6 会话失效

当前会话 Cookie 只证明签名和用户名，无法感知密码已经改变。实现必须为管理员
凭证增加单调递增的 `admin_session_revision`：

- 首次兼容读取时缺少该字段，按 `0` 处理；
- 登录创建的会话必须写入当前修订号；
- 每次受保护请求必须比较 Cookie 修订号和当前凭证修订号；
- 密码在线修改或离线重置成功后，修订号必须加一；
- 修订号不一致的会话统一返回未认证；
- 修改密码接口成功后主动删除当前 Cookie，前端返回登录页。

升级前创建且不含修订号的 Cookie 在修订号仍为 `0` 时继续有效。第一次密码修改
或离线重置后，所有旧 Cookie 同时失效。

不得通过轮换 `SECRET_KEY` 实现会话失效。`SECRET_KEY` 仍遵守 ADR-0004 的
持久化和不可隐式轮换约束。

## 5. 持久化契约

v0.2 不新增数据库表或 Alembic 迁移。默认 Appliance 继续以
`runtime-secrets.json` 作为管理员密码的持久化来源，并向现有 JSON 增加一个可选
字段：

```json
{
  "version": 1,
  "secret_key": "...",
  "credential_encryption_key": "...",
  "admin_password": "...",
  "admin_session_revision": 1
}
```

兼容规则：

- 缺少 `admin_session_revision` 时读取为 `0`；
- 写回时必须包含该字段；
- 未知字段不得导致敏感值被输出到日志；
- 文件权限继续保持 `0600`，配置目录继续保持 `0700`；
- 更新继续使用已有的同目录临时文件、`os.replace()` 和目录 `fsync` 策略；
- 备份和恢复边界仍是完整 `/data`，不得只备份 SQLite 数据库。

本阶段保留现有明文 `admin_password` 格式，避免把“在线修改密码”和“凭证格式
迁移”合并为一个高风险变更。密码哈希化需要单独的安全设计 PR、格式版本迁移和
离线重置兼容方案。

## 6. 部署模式边界

### 6.1 默认 Appliance

默认单容器 Appliance 是 v0.2 在线修改密码的完整支持范围：

- Launcher 首次启动或离线重置时维护同一份持久化文件；
- API 通过受控凭证组件在线更新该文件；
- Scheduler 和 Worker 不读取管理员密码，也不需要重启；
- 容器重启后 Launcher 读取在线修改后的值，不得被镜像默认 `admin` 覆盖。

### 6.2 高级 Compose

高级 Compose 当前由外部 `.env` 中的 `ADMIN_PASSWORD` 管理密码，MediaSync
不能安全地反向修改宿主机 `.env`。v0.2 实现必须显式识别该模式：

- 状态接口向前端返回是否支持在线修改；
- 不支持时，修改接口返回 `409 Conflict` 和不含敏感值的操作说明；
- 前端展示“请修改 `.env` 中的 `ADMIN_PASSWORD` 并重建 API 容器”；
- 不得让接口看似成功、但下次 Compose 重建又恢复旧密码。

未来如果高级 Compose 统一采用 `/data` 中的管理员凭证来源，必须用独立设计 PR
修改该边界。

## 7. API 契约

### 7.1 查询能力

现有接口：

```http
GET /api/v1/auth/status
```

响应增加：

```json
{
  "authenticated": true,
  "username": "admin",
  "password_change_supported": true
}
```

未登录时仍可返回 `authenticated: false`，但不得暴露密码状态、修订号或部署密钥。

### 7.2 修改密码

```http
POST /api/v1/auth/password
Content-Type: application/json
```

请求：

```json
{
  "current_password": "当前密码",
  "new_password": "新的强密码",
  "confirm_password": "新的强密码"
}
```

成功：

```http
HTTP/1.1 200 OK
Set-Cookie: mediasync_session=; Max-Age=0; Path=/
```

```json
{
  "message": "密码已修改，请重新登录"
}
```

错误语义：

| HTTP 状态 | 场景 |
|---:|---|
| `401` | 当前会话缺失、过期或修订号失效 |
| `409` | 当前部署模式不支持在线修改 |
| `422` | 字段缺失、确认不一致、密码不满足规则或与旧密码相同 |
| `503` | 持久化文件无法安全更新 |

当前密码错误也返回 `422` 的通用校验错误，不在响应中区分内部校验步骤。

响应、异常、访问日志和结构化日志不得包含三个请求字段的值。

## 8. 前端交互

管理员区域增加“修改密码”入口。v0.2 可以使用独立对话框，不新增复杂设置中心。

交互要求：

- 三个输入框都使用密码类型，并支持用户主动显示；
- 浏览器自动完成分别使用 `current-password` 和 `new-password`；
- 前端先检查确认值，但后端必须重复校验；
- 成功后清空本地认证状态并跳转登录页；
- 不在 `localStorage`、URL、通知详情或错误日志中保存密码；
- 部署模式不支持时隐藏提交操作并显示离线修改说明；
- 默认密码登录时可以提示修改，但不得阻断用户进入后台。

## 9. 失败与恢复

| 场景 | 必须结果 |
|---|---|
| 当前密码错误 | 无任何状态变化 |
| 新密码校验失败 | 无任何状态变化 |
| 临时文件写入失败 | 旧密码和旧会话继续有效 |
| 原子替换后 API 崩溃 | 重启后新密码有效，旧会话因修订号失效 |
| 响应发送前网络断开 | 服务端结果以持久化文件为准，用户可用新密码重新登录确认 |
| 两个修改请求并发 | 最多一个成功 |
| 在线修改后重启 Appliance | 新密码保持有效 |
| 使用新 `ADMIN_PASSWORD` 离线重置 | 密码更新、修订号递增、全部旧会话失效 |
| 镜像默认 `admin` 重启已有 `/data` | 不覆盖在线设置的密码 |
| 恢复旧 `/data` 备份 | 密码和修订号一起恢复，以备份时状态为准 |

## 10. 可观测性与审计

v0.2 不新增完整安全审计表，只记录不含敏感值的结构化事件：

```text
admin_password_change_succeeded source=web
admin_password_change_failed reason=validation
admin_password_change_failed reason=persistence
admin_password_reset_succeeded source=environment
```

日志不得记录：

- 当前密码或新密码；
- 密码长度、前后缀或字符类别；
- Cookie、签名内容或 `admin_session_revision`；
- `SECRET_KEY` 或 `CREDENTIAL_ENCRYPTION_KEY`。

## 11. 验收要求

### 11.1 后端

- 未登录请求被拒绝；
- 当前密码错误、确认不一致、弱密码和重复密码均无状态变化；
- 合法修改原子更新文件与内存凭证；
- 修改成功后旧密码不能登录，新密码可以登录；
- 修改前创建的全部 Cookie 失效；
- 并发修改最多一个成功；
- 写入失败时旧密码和旧会话保持有效；
- v0.1/现有 v0.2 无修订号文件可兼容读取；
- 在线修改和离线重置后，容器重启语义一致；
- 高级 Compose 返回明确的 `409`，不制造虚假持久化。

### 11.2 前端

- 支持状态为真时可以完成修改；
- 三个字段不会进入 URL 或持久化存储；
- 成功后立即退出并跳转登录页；
- 后端错误使用中文、可操作且不泄露敏感信息；
- 不支持的部署模式展示离线修改说明。

### 11.3 Appliance

- 使用临时 `/data` 启动并以默认密码登录；
- 在线修改密码；
- 验证所有旧会话失效；
- 重启同一容器和重建同一数据卷后，新密码仍有效；
- 使用环境变量离线重置后，在线设置的旧密码和旧会话均失效；
- 日志扫描确认没有出现测试密码。

## 12. 实现拆分

设计 PR 合并后创建一个独立运行时 Issue，并拆成可审查的实现顺序：

1. 管理员凭证 Store、修订号兼容读取和原子更新测试；
2. 会话修订号、修改密码 API 和后端契约测试；
3. 前端修改密码入口与交互；
4. Appliance 重启、离线重置和日志脱敏验收；
5. 更新用户部署文档。

实现可以在一个小型运行时 PR 中完成，但不得顺带加入登录限流、多用户、密码哈希
迁移或设置中心重构。
