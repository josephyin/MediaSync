# ADR-0003：单一发布镜像，多进程容器拓扑

- 状态：已由 ADR-0004 取代
- 日期：2026-07-28
- 决策者：MediaSync 维护者
- 取代：无
- 被取代：ADR-0004
- 相关内容：[v0.2.0-rc.2 单镜像部署设计](../single-image-deployment-rc2.md)

## 背景

MediaSync 的 API、Scheduler、Worker、迁移和对账已经复用一个后端镜像，Vue
管理后台使用单独的 Nginx 镜像。双镜像保持了运行时内容精简，但增加了 NAS
部署配置、版本配对和发布验证成本。

项目希望每个版本只有一个可分发的 OCI 产物，同时不能退回 API 内执行调度和
任务的单进程工具架构。

## 决策

MediaSync 从 v0.2.0-rc.2 开始发布一个包含后端运行时、Nginx 和前端静态资源的
`mediasync` 镜像。

官方 Compose 的迁移、对账、API、Scheduler、Worker 和 frontend 服务都引用
同一个精确镜像版本，并通过显式命令启动各自唯一的主进程。

单一镜像是发布边界，不是进程边界。项目继续使用多个容器隔离职责，不引入
Supervisor 或容器内多进程编排。

## 不变量

- 一个常驻容器只运行一个主进程。
- API 不执行扫描或转存。
- Scheduler 只发现到期订阅并创建任务。
- Worker 是唯一任务执行者。
- SQLite 只支持一个 Scheduler 和一个 Worker。
- 迁移和对账继续作为常驻进程启动前的屏障。
- 一个部署中的所有服务引用同一个精确镜像标签。
- 精确版本标签发布后不可覆盖。
- 单镜像改造不得改变数据库契约或远端操作语义。

## 后果

收益：

- NAS 用户只需配置和拉取一个镜像；
- 前端、后端不再出现版本配对错误；
- 每个版本只需验证一个多架构 OCI 产物；
- GHCR 和 Docker Hub 的发布契约更简单。

成本：

- 每个容器都会携带部分未使用的运行时内容；
- 镜像体积和构建时间可能增加；
- Nginx 与 Python 基础环境的安全更新需要统一发布；
- 前端与后端不能再独立发布。

## 已考虑的备选方案

### 保持两个镜像

运行时内容最精简，也符合常见前后端拆分方式，但没有解决用户希望简化 NAS
部署和版本配对的问题。

### 单容器运行全部进程

可以进一步减少容器数量，但需要 Supervisor 或自定义进程管理器，会重新耦合
生命周期、健康检查和故障恢复，违反 v0.2 已建立的进程边界，因此拒绝。

### 由 FastAPI 提供前端静态文件

可以移除 Nginx，但会把静态资源、反向代理和缓存职责放回 API，改变现有部署
行为，也降低以后替换网关的灵活性，因此不采用。

### 一个 Docker Hub 仓库使用多个功能标签

例如 `backend-v0.2.0` 和 `frontend-v0.2.0`。这只减少仓库数量，仍然是两个
镜像产物，不能消除版本配对，因此不作为单镜像方案。

## 未来复审

出现以下情况时，应通过新 ADR 复审本决定：

- 单镜像体积或漏洞面显著影响 NAS 部署；
- 前后端需要独立发布周期；
- 项目引入外部网关，镜像内不再需要 Nginx；
- 支持的编排平台需要按职责使用最小化镜像；
- 实际维护成本长期高于单一发布产物带来的便利。
